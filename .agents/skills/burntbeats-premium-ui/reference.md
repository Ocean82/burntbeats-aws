# Cursor Skill: Premium UI / UX for Burnt Beats Audio + MIDI Surfaces

## Purpose
This skill governs how the agent designs and implements frontend interfaces for a professional-grade web application centered on:
- stem separation
- waveform visualization
- in-browser mixing/export
- audio-to-MIDI conversion
- piano-roll-based MIDI editing
- lightweight DAW workflows
- subscription-aware SaaS UX

This skill is intentionally designed to:
- align with the existing architecture rather than refactor it
- preserve the current separation between waveform/stem workflows and MIDI/DAW workflows
- improve professionalism, polish, and conversion quality
- avoid generic “AI-generated” UI
- produce interfaces that feel as if a seasoned product and frontend team built them over multiple years

---

## 1. Prime Directive

When building UI, act like a:
- senior product designer
- frontend architect
- interaction designer for creative software
- design systems engineer
- conversion-aware SaaS UX strategist

All output must feel:
- premium
- deliberate
- highly usable
- visually distinctive
- audio-domain aware
- commercially intentional
- handcrafted, not templated

Do not design like a solo side-project dashboard.
Do not produce plain, basic, sparse, or obviously autogenerated surfaces.
Aim for the visual maturity of a polished commercial creative tool.

---

## 2. Scope and Refactor Boundaries

### 2.1 Respect Existing Architecture
This project already has established product surfaces, workflows, and service boundaries.
Enhance them. Do not aggressively re-platform or reorganize the application unless explicitly asked.

### 2.2 Do Not Trigger Unnecessary Refactors
Unless directly requested, do **not**:
- replace the frontend stack
- migrate the routing model
- invent a new design system from scratch that forces sweeping rewrites
- consolidate distinct feature pages into one giant editor
- re-architect service boundaries
- redesign backend API contracts
- rename broad application concepts unnecessarily
- introduce speculative infrastructure changes

### 2.3 Preferred Behavior
The agent should:
- improve visual quality
- improve interaction quality
- improve component consistency
- improve feature discoverability
- modernize and refine layouts
- add needed DAW/MIDI tools thoughtfully
- preserve the app’s current conceptual organization

### 2.4 Deliberate Vagueness Rule
Leave implementation room where useful.
Do not over-prescribe every structural detail in a way that causes large-scale rewrites.
Be specific enough to guide quality and consistency, but flexible enough to work with the current codebase.

## 3. Current Stack and Hard Constraints

### 3.1 Required Stack Alignment
Assume the active stack is:

- React 19 + TypeScript for frontend
- Vitest + Playwright for testing
- Express for backend orchestration / API
- Python `stem_service` with boto3 integration
- AWS S3 presign/proxy patterns for file delivery

Design and implementation guidance must fit this stack without trying to swap it out.

### 3.2 Processing Constraint
Production stem separation is **CPU-only**.

Non-negotiable:
- do not add GPU-dependent code paths
- do not assume CUDA/WebGPU/Metal inference paths
- keep Demucs / MDX behavior aligned with existing CPU-oriented `prefer_speed` and `quality_mode` expectations
- prefer interface patterns that make CPU processing feel responsive through strong async UX, not through unrealistic system assumptions

### 3.3 Frontend Behavior Constraint
Design for the existing architecture, then improve quality inside that architecture.
The goal is to elevate precision, polish, and cohesion — not to destabilize working flows.

- upload

- waveform display
- track/stem preview
- mixing
- export

- audition / transport / loop workflows

These pages should feel like part of one premium product family, but they must not be visually or functionally identical.

Use:
- shared typography
- shared spacing rhythm
- shared color principles
- shared shell / navigation patterns
- shared interaction quality

But preserve:
- distinct controls
- distinct panel structure

The waveform workspace should feel optimized for audio separation and listening.
The MIDI/DAW workspace should feel optimized for composition, timing, note editing, and arrangement.

## 6. Design System Guidance

### 6.1 Typography
Use a premium sans-serif variable stack such as:
- Inter Variable
- SF Pro equivalents where available
- high-quality system fallback
- monospace or tabular-numeric treatment for time and note data

Requirements:
- tabular numerals for timecodes, beat positions, BPM, dB, note lengths, MIDI values
- disciplined type hierarchy
- compact but readable labels
- mature panel headings, not oversized gamer UI labels

### 6.2 Color
Use a dark-first interface with controlled contrast and semantic accents.

Requirements:
- layered dark neutrals for canvas, panels, rails, overlays, and raised controls
- one brand-primary hue
- one active/accent hue
- semantic states for success, warning, error, info
- stable per-track/per-stem color logic
- color should reinforce meaning, not provide meaning alone

### 6.3 Spacing
Use a disciplined 4px grid.
The app should feel tight and professional, not loose and hobbyist.

### 6.4 Elevation
Create 3–4 clear planes:
- base canvas
- panel surfaces
- floating controls / popovers
- modal / overlay surfaces

### 6.5 Motion
Motion should:
- clarify state changes
- improve perceived responsiveness
- reinforce precision
- never feel flashy for its own sake

Use:
- 100–150ms microinteractions
- 200–250ms panel transitions
- 300ms expand/collapse only where appropriate

Respect reduced-motion settings.

### 8.1 Primary Experience Goals
This surface should feel optimized for:
- upload → process → preview → mix → export
- quick understanding of result quality
- low-friction comparison between stems
- confidence during long-running CPU jobs

### 8.2 Required Interface Elements
This workspace should strongly support:
- upload/dropzone
- job state / queue state / progress
- waveform visualization
- stem list or track lanes
- mute / solo / gain controls
- playback transport
- export/download actions
- plan/usage-aware affordances
- retry/reprocess flows

### 8.3 Waveform UX
Waveform interactions should feel:
- smooth
- precise
- stable
- professional

Support where appropriate:
- click-to-seek
- scrubbing
- zoom
- pan
- selection regions
- loop region feedback
- timeline ruler
- current-time display
- comparative listening workflows

### 8.4 Mixer Behavior
Mixer and stem controls should feel more like a real tool than a web form.
Use:
- refined track headers
- compact gain controls
- meaningful mute/solo active states
- clear arm/lock states when relevant
- polished meters if available
- grouped controls that prioritize frequent actions

### 8.5 CPU-Aware Async UX
Because processing is CPU-only:
- show strong progress feedback
- expose queue/processing/finalizing states clearly
- avoid frozen-looking screens
- allow users to remain oriented while waiting
- use optimistic layout readiness even when outputs are pending
- make “work in progress” feel intentional, not broken

## 9. MIDI / DAW Workspace Guidance

This workspace must feel like a legitimate lightweight web DAW / MIDI editor — not a toy piano roll pasted onto a generic page.

### 9.1 Primary Experience Goals
The MIDI/DAW surface should feel optimized for:
- transcription review
- note cleanup
- arrangement refinement
- rhythm correction
- melodic editing
- multi-track MIDI organization
- fast export and iteration

### 9.2 Core Visual Model
The MIDI page should center around a professional editing canvas composed of:

- top transport / timeline bar
- main piano roll editor
- track / lane sidebar
- lower utility lanes or inspector region
- optional right-side inspector / note detail / tool panel
- persistent tool affordances that do not clutter the main note canvas

### 9.3 Piano Roll Expectations
The piano roll should include, where relevant:

- vertical piano keyboard
- horizontal bar/beat timeline ruler
- visible grid subdivisions
- note blocks with strong contrast and refined rounding
- color logic by track, region, or selection state
- playhead line
- loop/selection region
- zoom controls
- pan/scroll behavior
- snapping feedback
- note labels or pitch awareness where useful
- strong selected-note visibility

The piano roll must look:
- dense but readable
- technical but beautiful
- modern without becoming minimal to the point of weakness
- like serious music software, not educational software

### 9.4 MIDI Editing Tools
The MIDI page should support customary editing tools expected of a modern web-based DAW-style editor, including where appropriate:

- pointer/select tool
- pencil/draw tool
- erase/delete interaction
- split/cut behavior
- multi-select / box select / lasso select
- drag note move
- drag note resize
- drag vertically to change pitch
- drag horizontally to change timing
- duplicate/copy/paste
- nudge left/right
- duplicate phrase / repeat pattern workflows
- undo/redo-aware editing patterns

### 9.5 Timing and Musicality Features
Strongly encourage the agent to support or visually account for:

- snap-to-grid
- bar / beat / subdivision grid visibility
- quantize access
- note start / end precision
- swing-aware or groove-aware language where relevant
- loop editing
- region repetition logic
- metronome awareness in the transport experience

Do not force full workstation-grade complexity where it would cause major refactors, but do preserve the look and behavior expectations of a serious sequencer.

### 9.6 Note Data Lanes / Lower Editor Lanes
The MIDI / DAW page should strongly consider lower-lane editing or inspector support for:

- velocity
- note length awareness
- note start timing refinement
- sustain / expression lanes if already compatible with the data model
- simple controller data visualization where feasible

At minimum, velocity editing should feel intentional and polished, not like an afterthought.

### 9.7 Multi-Track MIDI Behaviors
Where the product supports multiple MIDI results or merged outputs, the DAW page should be able to present:

- track list / lane list
- per-track color identity
- mute / solo / visibility states
- reorder affordances
- collapse/expand behavior
- selected-track focus
- easy switching between track editing contexts

The interface should make multi-track work understandable without becoming visually noisy.

### 9.8 Transport and Audition
The MIDI page should include a premium transport surface with typical DAW expectations:

- play / pause
- stop
- loop
- timeline position
- bar/beat or time readout
- optional BPM display where meaningful
- metronome toggle if supported
- quick audition of edited notes or selections
- clear playback focus

Playback state should feel tightly integrated with the piano roll, not detached.

### 9.9 Inspector / Context Tools
A refined note inspector or contextual editing region can include:
- selected note pitch
- start
- length
- velocity
- channel / track metadata if meaningful
- quantize shortcuts
- transpose shortcuts
- duplicate / delete shortcuts

Keep this compact and professional.
Do not let it become a giant form UI.

### 9.10 Visual Style of Notes and Grid
Notes should not look childish or overly flat.
Prefer:
- subtle depth
- tightly controlled borders
- premium accent treatment
- visible active-selection state
- hover affordance
- overlapping-note clarity
- track-based coloration that still preserves readability

The grid should feel polished:
- subdued but clear
- strong enough for timing work
- stronger contrast at bar lines than subdivisions
- understated but not invisible

### 9.11 Optional Advanced Features
If compatible with the existing codebase and task scope, the agent may also design for:
- ghost notes / faint neighboring context
- scale/key overlays
- chord-region guidance
- drum-lane mode or percussion labeling
- split-by-instrument visual grouping
- region headers or clips above the piano roll

These are optional enhancements, not mandatory refactor triggers.

### 9.12 DAW Realism Rule
The MIDI page should borrow cues from real creative tools:
- precise rulers
- compact inspectors
- dense but controlled interface rhythm
- professional selection states
- visible transport hierarchy
- serious editing affordances

The result should feel closer to a lightweight commercial DAW than to a generic MIDI demo.

## 13. Implementation Behavior for the Agent

When implementing or updating a feature, use this sequence:

1. Identify whether the task belongs to:
   - stem/waveform workspace
   - MIDI/DAW workspace
   - shared shell/system
2. Respect current architecture and avoid unnecessary broad refactors
3. Preserve current stack assumptions and CPU-only processing constraints
4. Define the most important user action for that surface
5. Improve layout, hierarchy, and interaction clarity first
6. Add polish, density control, and professional visual treatment second
7. Add empty/loading/error/success states
8. Ensure the feature feels premium and commercially viable
9. Ensure the result does not look generic, hobbyist, or autogenerated
10. Stop short of rewiring unrelated systems unless explicitly instructed
