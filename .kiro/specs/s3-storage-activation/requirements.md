# Requirements Document

## Introduction

This feature activates the existing S3 storage pipeline in BurntBeats for production use. The infrastructure is already built — Python stem service uploads to S3, Node backend generates presigned URLs, and the frontend transparently follows redirects — but the pipeline has never been enabled end-to-end. This spec covers the phased activation: environment configuration, CORS setup, database migration, integration testing, production deployment, and post-launch optimization.

## Glossary

- **Stem_Service**: The Python service (`stem_service/`) that performs AI audio stem separation and uploads results to S3 when enabled.
- **Backend**: The Node.js Express API (`backend/`) that serves stem files via presigned S3 URLs or disk fallback.
- **Frontend**: The React SPA (`frontend/`) that fetches stems via `/api/stems/file/...` regardless of storage backend.
- **S3_Pipeline**: The complete flow from stem upload (`s3_upload.py`) through presigned URL generation (`s3Presign.js`) to browser redirect (`file-serve.js`).
- **Progress_JSON**: The `progress.json` file written per job containing status, stem list, and optional `s3` metadata (bucket, region, per-stem keys).
- **Presigned_URL**: A time-limited S3 GET URL generated by the Backend that allows the browser to download a stem file directly from S3 without AWS credentials.
- **Stems_Table**: The PostgreSQL `stems` table storing per-stem metadata including `s3_key` for re-download capability.
- **CORS_Policy**: Cross-Origin Resource Sharing rules on the S3 bucket that allow browsers to follow presigned URL redirects from the app origin.
- **IAM_Credentials**: AWS access key and secret key with permissions to read/write the S3 bucket.
- **Upsert**: An INSERT that updates the existing row on conflict (used for `stems` table when S3 keys arrive after initial insert).
- **My_Stems_Page**: The user-facing React view that displays stem separation history and enables re-download of previously processed stems from S3.
- **Job_Card**: A UI component representing a single stem separation job, showing the original filename, date, stem count, and expandable detail section.

## Requirements

### Requirement 1: Environment Configuration and Credential Verification

**User Story:** As a DevOps engineer, I want all S3 environment variables correctly configured and verified across all services, so that the S3 pipeline can operate in production without credential failures.

#### Acceptance Criteria

1. WHEN `S3_ENABLED=true` is set in the Stem_Service environment, THE Stem_Service SHALL attempt S3 upload after each completed job.
2. WHEN the Backend container starts, THE Backend SHALL have access to `S3_BUCKET`, `S3_PREFIX`, `S3_REGION`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY` environment variables via docker-compose.yml.
3. WHEN the Stem_Service container starts, THE Stem_Service SHALL have access to `S3_ENABLED`, `S3_BUCKET`, `S3_REGION`, `S3_PREFIX`, and AWS credential variables via docker-compose.yml.
4. WHEN a credential verification script is executed, THE script SHALL confirm `s3:PutObject`, `s3:GetObject`, and `s3:ListBucket` permissions on the `burntbeatz2-storage` bucket.
5. IF AWS credentials are missing or invalid, THEN THE Stem_Service SHALL log a warning and skip S3 upload without failing the job.
6. IF AWS credentials are missing or invalid, THEN THE Backend SHALL fall back to serving stems from local disk without error.
7. THE root `.env` file SHALL contain `S3_ENABLED=true`, `S3_BUCKET=burntbeatz2-storage`, `S3_REGION=us-east-1`, `S3_PREFIX=stems`, and `S3_DELETE_LOCAL_AFTER_UPLOAD=false`.

### Requirement 2: S3 Bucket CORS Configuration

**User Story:** As a frontend developer, I want the S3 bucket to have correct CORS rules, so that browsers can follow presigned URL redirects and load stem audio files without silent failures.

#### Acceptance Criteria

1. THE S3 bucket `burntbeatz2-storage` SHALL have a CORS configuration that allows `GET` requests from the production origin (`https://burntbeats.com`, `https://www.burntbeats.com`).
2. THE CORS_Policy SHALL allow the `Authorization`, `Range`, and `Content-Type` headers in requests.
3. THE CORS_Policy SHALL expose the `Content-Length`, `Content-Type`, `ETag`, and `Content-Range` response headers to the browser.
4. WHEN a browser follows a 302 redirect to a Presigned_URL, THE S3 bucket SHALL respond with appropriate CORS headers allowing the audio data to be read by the Frontend.
5. THE CORS_Policy SHALL include `http://localhost:5173` and `http://localhost:3000` as allowed origins for local development.
6. WHEN a CORS setup script is executed, THE script SHALL apply the CORS configuration idempotently (safe to re-run).

### Requirement 3: Database Schema Migration

**User Story:** As a backend developer, I want the `stems` table to support upsert behavior with a UNIQUE constraint, so that S3 keys can be recorded reliably even when the async upload completes after the first status poll.

#### Acceptance Criteria

1. THE Stems_Table SHALL have a UNIQUE constraint on `(job_id, stem_name)` to support upsert behavior.
2. WHEN `insertStems()` is called with S3 keys for a job that already has stem rows, THE Backend SHALL update the existing rows with the new `s3_key` values using `ON CONFLICT DO UPDATE`.
3. WHEN a job reaches `completed` status, THE Backend status polling route SHALL call `insertStems()` with stem metadata including any available S3 keys from Progress_JSON.
4. IF the `stems` table contains duplicate `(job_id, stem_name)` rows from before the constraint, THEN THE migration SHALL remove duplicates (keeping the earliest row) before adding the constraint.
5. THE migration SHALL be idempotent — safe to run multiple times without error.
6. WHEN `insertStems()` is called and the database pool is unavailable, THE Backend SHALL log the error and continue without failing the request.

#### Phase 3 Implementation Details

**Tools needed:**
- PostgreSQL client (`psql` or `node backend/db-migrate.js`)
- AWS RDS access (via bastion or direct if security group allows)

**Reference files:**
- `backend/db-schema.sql` (stems table definition — already has UNIQUE constraint in schema)
- `backend/migrations/001_stems_unique_constraint.sql` (migration already written)
- `backend/db-jobs.js` (`insertStems()` — already uses ON CONFLICT DO UPDATE)
- `backend/routes/stems/status.js` (already calls `insertStems()` on completion)

**Files to alter:**
- `backend/db-migrate.js` — ensure it runs `001_stems_unique_constraint.sql`
- Potentially no code changes needed — the migration and code are already written

**Files requiring caution:**
- `backend/migrations/001_stems_unique_constraint.sql` — the DELETE for duplicates must run before ALTER TABLE; if the table has millions of rows, this could lock the table briefly
- `backend/db-jobs.js` — the `insertStems()` parameterized query uses `$` placeholders that must stay correctly indexed

**Verification check:**
```bash
# 1. Run migration
node backend/db-migrate.js
# 2. Verify constraint exists
psql "$DATABASE_URL" -c "\d stems" | grep "stems_job_id_stem_name_key"
# 3. Test upsert behavior
psql "$DATABASE_URL" -c "
  INSERT INTO stems (job_id, stem_name, s3_key) VALUES ('00000000-0000-0000-0000-000000000001', 'vocals', 'test/key1')
  ON CONFLICT (job_id, stem_name) DO UPDATE SET s3_key = EXCLUDED.s3_key;
  SELECT s3_key FROM stems WHERE job_id = '00000000-0000-0000-0000-000000000001' AND stem_name = 'vocals';
"
# Expected: test/key1
# 4. Clean up test row
psql "$DATABASE_URL" -c "DELETE FROM stems WHERE job_id = '00000000-0000-0000-0000-000000000001';"
```

**Flexibility notes:**
- If the migration fails due to existing duplicates with complex data, manually inspect with `SELECT job_id, stem_name, COUNT(*) FROM stems GROUP BY job_id, stem_name HAVING COUNT(*) > 1` before running.
- If the table is empty (likely, since S3 was never enabled), the duplicate-removal step is a no-op and the constraint adds instantly.

### Requirement 4: Integration Testing (Local)

**User Story:** As a developer, I want to verify the complete S3 pipeline works end-to-end locally, so that I can confirm stems upload to S3, presigned URLs are generated, and the frontend can load audio before deploying to production.

#### Acceptance Criteria

1. WHEN a stem separation job completes with `S3_ENABLED=true`, THE Stem_Service SHALL upload all stem WAV files to S3 under the key pattern `{S3_PREFIX}/{job_id}/stems/{filename}`.
2. WHEN S3 upload succeeds, THE Stem_Service SHALL write `s3` metadata (bucket, region, keys map) into Progress_JSON.
3. WHEN the Backend serves `GET /api/stems/file/:job_id/:stemId` and Progress_JSON contains S3 metadata for that stem, THE Backend SHALL respond with a 302 redirect to a Presigned_URL.
4. WHEN the Frontend fetches a stem file URL and receives a 302 redirect to a Presigned_URL, THE Frontend SHALL successfully load the audio data as an ArrayBuffer.
5. IF S3 upload has not yet completed when the first status poll occurs (due to async daemon thread), THEN THE Backend SHALL serve the stem from local disk until S3 metadata appears in Progress_JSON.
6. WHEN the Presigned_URL expires (default 3600 seconds), THE S3 bucket SHALL return 403 Forbidden, and THE Frontend SHALL display an appropriate error to the user.

#### Phase 4 Implementation Details

**Tools needed:**
- Docker Compose (full stack: `docker compose up`)
- `curl` for API testing
- Browser for end-to-end audio playback verification
- AWS CLI for verifying S3 objects exist

**Reference files:**
- `stem_service/s3_upload.py` (`upload_job_stems_to_s3` — the upload function)
- `stem_service/job_utils.py` (`schedule_s3_upload` — async daemon thread)
- `stem_service/job_worker.py` (calls `schedule_s3_upload` after completion)
- `backend/routes/stems/file-serve.js` (302 redirect logic)
- `backend/routes/stems/status.js` (calls `insertStems` with S3 keys)
- `backend/s3Presign.js` (`presignStemGetUrl`)
- `frontend/src/api/stems.ts` (`fetchStemWavAsArrayBuffer`)

**Files to alter:**
- None — this phase is testing only

**Files requiring caution:**
- The async S3 upload runs in a daemon thread (`schedule_s3_upload`). If the stem_service container restarts before the thread completes, the upload is lost. Progress_JSON will lack `s3` metadata and the backend falls back to disk. This is acceptable but must be understood.
- `S3_DELETE_LOCAL_AFTER_UPLOAD` MUST remain `false` during testing to preserve the disk fallback.

- If the daemon thread upload is too slow for testing, temporarily set a short sleep or use a synchronous upload path for verification.
- If CORS issues appear in the browser but `curl` works, the problem is CORS configuration (Phase 2) not the S3 pipeline itself.
- If presigned URLs return 403, check that the Backend's AWS credentials have `s3:GetObject` permission (the presigner needs it even though it doesn't download the file itself).

### Requirement 5: Production Deployment and Monitoring

**User Story:** As an operations engineer, I want to deploy S3 storage to production with safety nets and monitoring, so that I can detect failures early and fall back to disk serving if needed.

#### Acceptance Criteria

1. WHEN deployed to production, THE system SHALL have `S3_DELETE_LOCAL_AFTER_UPLOAD=false` to maintain local disk copies as a safety net.
2. WHILE `S3_DELETE_LOCAL_AFTER_UPLOAD=false`, THE Backend SHALL serve stems from S3 (via presigned redirect) when S3 metadata exists, and from local disk otherwise.
3. WHEN an S3 upload fails for a job, THE Stem_Service SHALL log the failure with job_id and stem names, and THE Backend SHALL continue serving from disk.
4. WHEN a presigned URL generation fails, THE Backend SHALL log the error and fall back to streaming the stem from local disk.
5. WHEN a job completes successfully with S3 upload, THE Stems_Table SHALL contain rows with non-null `s3_key` values for each stem of that job.
6. THE system SHALL log S3 upload success/failure counts that can be monitored via Sentry or log aggregation.

**Tools needed:**

**Files to alter:**

**Files requiring caution:**

### Requirement 6: Post-Launch Optimization

**User Story:** As a product owner, I want to optimize storage costs and enable customer-facing features once S3 is proven reliable, so that disk space is reclaimed and users can re-download their stems.

#### Acceptance Criteria

1. WHEN S3 upload success rate exceeds 99% over 7 days, THE system SHALL be eligible to enable `S3_DELETE_LOCAL_AFTER_UPLOAD=true`.
2. WHILE `S3_DELETE_LOCAL_AFTER_UPLOAD=true`, THE Stem_Service SHALL delete local WAV files after successful S3 upload confirmation.
3. WHEN `S3_DELETE_LOCAL_AFTER_UPLOAD=true` is enabled, THE Backend SHALL rely exclusively on S3 presigned URLs for stem serving (no disk fallback for uploaded stems).
4. WHERE S3 lifecycle policies are configured, THE S3 bucket SHALL transition objects older than 90 days to Infrequent Access storage class for cost reduction.
5. WHERE CloudFront CDN is configured, THE system SHALL serve presigned URLs through CloudFront for reduced latency on global downloads.
6. WHEN a user requests their stem history, THE Backend SHALL query the Stems_Table and generate fresh Presigned_URLs for re-download of previously separated stems.

#### Phase 6 Implementation Details

**Tools needed:**
- AWS CLI (`aws s3api put-bucket-lifecycle-configuration`)
- AWS Console (CloudFront distribution setup)
- Application code changes for "My Stems" feature

**Reference files:**
- `stem_service/s3_upload.py` (local file deletion logic — already implemented, gated by env var)
- `backend/db-jobs.js` (`getJobHistory` — existing query for user's jobs)
- `backend/s3Presign.js` (`presignStemGetUrl` — can generate URLs from stored `s3_key`)
- `backend/db-schema.sql` (stems table with `s3_key` column)

**Files to alter:**
- `.env` on production — change `S3_DELETE_LOCAL_AFTER_UPLOAD=true` when ready
- New file: `scripts/s3-lifecycle-policy.json` (lifecycle rules)
- Future: new API route for "My Stems" re-download feature
- Future: CloudFront distribution configuration

**Files requiring caution:**
- Once `S3_DELETE_LOCAL_AFTER_UPLOAD=true` is set, there is NO disk fallback. If S3 becomes unavailable, stems are inaccessible until S3 recovers. Only enable after thorough monitoring.
- S3 lifecycle policies that delete objects (not just transition) would permanently destroy stems. Use transition-only policies initially.

**Verification check:**
```bash
# 1. Check S3 upload success rate over past 7 days
psql "$DATABASE_URL" -c "
  SELECT
    COUNT(*) FILTER (WHERE s3_key IS NOT NULL) as with_s3,
    COUNT(*) as total,
    ROUND(100.0 * COUNT(*) FILTER (WHERE s3_key IS NOT NULL) / NULLIF(COUNT(*), 0), 2) as success_pct
  FROM stems
  WHERE created_at > now() - interval '7 days';
"
# 2. If success_pct >= 99%, enable deletion
# Update .env: S3_DELETE_LOCAL_AFTER_UPLOAD=true
# 3. Verify disk space is being reclaimed
df -h /app/tmp/stems
# 4. Apply lifecycle policy
aws s3api put-bucket-lifecycle-configuration \
  --bucket burntbeatz2-storage \
  --lifecycle-configuration file://scripts/s3-lifecycle-policy.json
```

**Flexibility notes:**
- If CloudFront is added, presigned URLs change format (CloudFront signed URLs vs S3 presigned URLs). This requires updating `s3Presign.js` to use CloudFront key pairs instead of S3 signing.
- The "My Stems" feature can be built incrementally — start with a simple API endpoint that returns presigned URLs for a user's stems, then add a frontend UI later.
- If cost is a concern before lifecycle policies, consider setting a shorter presign expiry (e.g., 1800s instead of 3600s) to reduce the window for unauthorized access.

### Requirement 7: My Stems Page — User-Facing Stem History and Re-Download UI

**User Story:** As a music producer, I want to browse my past stem separation jobs and re-download individual stems or full ZIP bundles from S3, so that I can access my processed audio files at any time without re-running separation jobs.

#### Acceptance Criteria

1. WHEN a user navigates to the "My Stems" view, THE Frontend SHALL display a list of the user's past stem separation jobs as expandable cards, ordered by most recent first.
2. WHEN a user expands a job card, THE Frontend SHALL reveal individual stem rows showing stem name, file size, and a download button for each stem.
3. WHEN a user clicks "Download" on an individual stem, THE Frontend SHALL fetch a fresh Presigned_URL from the Backend and initiate a browser download of that stem file.
4. WHEN a user clicks "Download All" on a job card, THE Frontend SHALL fetch Presigned_URLs for all stems in that job, bundle them into a ZIP file client-side, and initiate a browser download.
5. THE Frontend SHALL display a storage overview section showing total stems count, total jobs count, and approximate storage used (sum of `file_size_bytes` from the Stems_Table).
6. WHEN a user types in the search field, THE Frontend SHALL filter visible job cards by original filename, matching case-insensitively against partial text.
7. WHEN a user selects a sort option, THE Frontend SHALL re-order job cards by date (newest/oldest), file name (A-Z/Z-A), or stem count.
8. WHEN the Backend receives `GET /api/stems/history`, THE Backend SHALL return the authenticated user's job history joined with stem metadata from the Stems_Table, including `s3_key` for each stem.
9. IF a stem has no `s3_key` (S3 upload did not complete), THEN THE Frontend SHALL display that stem as "Unavailable" with a disabled download button.
10. IF Presigned_URL generation fails for a stem, THEN THE Backend SHALL return an error for that stem and THE Frontend SHALL display a toast notification explaining the download is temporarily unavailable.
11. THE Frontend SHALL use the existing BurntBeats dark theme (background `bg-[#1a1412]`, amber-500 accents, white text) and Framer Motion for expand/collapse animations.
12. THE Frontend SHALL be responsive, rendering a single-column card layout on mobile viewports and adapting touch targets for tap interaction.

**Flexibility notes:**
- The page can be implemented as a new view within the existing SPA (using the `activeView` state pattern already used for "editor" and "pricing") or as a separate route if React Router is added later.
- The storage overview stats can initially be computed client-side from the API response (sum of `file_size_bytes`). A dedicated backend stats endpoint can be added later if the dataset grows large.
- If the user has no stem history (new account or S3 was just enabled), show an empty state with a CTA to "Split your first track."
- The expandable card pattern (click to reveal stems) keeps the page clean without requiring a separate detail view — matching the user's preference for "expanding selections."
- Pagination can be deferred to a follow-up if the initial `LIMIT 50` from `getJobHistory` is sufficient for early users. Add infinite scroll or "Load More" when needed.
- The "Download All as ZIP" feature reuses the existing JSZip dependency and the sequential-fetch-on-mobile pattern from `useExport.ts`, so no new dependencies are needed.
